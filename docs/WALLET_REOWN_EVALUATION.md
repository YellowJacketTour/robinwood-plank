# Reown AppKit evaluation for plank.love wallet connectivity

**Date:** 2026-07-30 (docs fetched live from docs.reown.com / reown.com on this date)

## Recommendation

**Adopt Reown AppKit narrowly — as a replacement for the hand-built WalletConnect QR layer only (`lib/wallet-connect.ts` + `components/ConnectWalletModal.tsx`) — and keep `lib/wallet.ts` exactly as it is.** AppKit's Ethers adapter (`@reown/appkit-adapter-ethers`) does not require wagmi or viem, sits on top of ethers v6 the same way our current code does, and would delete the 4.75MB hand-built bundle in favor of a maintained, versioned package — but this is a real dependency addition with real bundle/session-model risk, so it should ship flag-gated in its own phase, after the concurrent wallet-state-fix and nav work lands, not bundled into this pass.

## What we actually have today (verified, not assumed)

- **No `@walletconnect/*`, `wagmi`, or `reown` package is in `package.json`** (checked `dependencies`, `devDependencies`, and full `package-lock.json`). `viem` appears in the lockfile only as a transitive dependency of `hardhat-gas-reporter` (a dev/test tool) — it is not reachable from any app code.
- `public/wallet-connect-bundle.js` is **4,862,013 bytes** and there is **no build script anywhere in the repo** that produces it (`package.json` has no `build:wallet-connect`-style script, and nothing under `scripts/` references WalletConnect or esbuild-bundles it). It was built once, out-of-band, with something like esbuild (its minifier fingerprint — `__esm`, `__commonJS`, `__toESM` helpers — is esbuild's), and committed as a static binary blob. This is exactly the "hand-built artifact" the owner suspected: nobody today can regenerate or patch it from `npm install` + a script. That's a real maintenance liability independent of Reown.
- `lib/wallet-connect.ts` lazily `import()`s that bundle at runtime, wraps `EthereumProvider.init()` from `@walletconnect/ethereum-provider` (bundled inside), and exposes a `preferredProvider` singleton that `lib/wallet.ts` consults via `getEthereumProvider()`.
- `lib/wallet.ts` is the safety-critical layer: `assertSafeSwapDestination` hard-allowlists transaction targets by `kind` (`swap` → Universal Router only, `approve` → Permit2/$PLANK only, `market`/`vault` → Seaport/vault/collection allowlists, `beacon` → the drand beacon address only), `simulateTransaction` runs `eth_call` + `eth_estimateGas` before every non-approve send and hard-fails closed on revert, and `sendTransaction` re-checks chain ID immediately before broadcast (TOCTOU guard) and re-derives gas floors per tx kind. None of this depends on WalletConnect specifically — it operates on a generic EIP-1193 `{request}` provider object, which is exactly the shape both the injected-wallet path and the current WalletConnect path already satisfy.
- `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` and the "get one free at cloud.reown.com" copy in `ConnectWalletModal.tsx` confirm: **WalletConnect Cloud and Reown Cloud are the same project/credential system today** — cloud.reown.com is WalletConnect Cloud's current name. No new credential needs to be provisioned to try AppKit; the existing project ID is reusable as-is.
- Chain 4663 (Robinhood Chain) is passed today as `chains: [CHAIN.id]` / `optionalChains: [CHAIN.id]` directly into `EthereumProvider.init()` — i.e., the current code already registers a fully custom EVM chain with WalletConnect's core SDK, no special support was needed.

## What Reown AppKit provides today (fetched from docs.reown.com, 2026-07-30)

1. **Framework requirements — critical finding: AppKit does NOT require wagmi/viem.** AppKit ships adapters per stack. The Ethers adapter path (`@reown/appkit @reown/appkit-adapter-ethers ethers`) is a first-class, documented install target alongside the Wagmi adapter — wagmi/viem are only pulled in if you pick *that* adapter. AppKit's docs describe the Ethers adapter as supplying the wallet/session layer while "your application code maintains responsibility for transaction logic using standard Ethers APIs" — i.e., it plugs into `getEthereumProvider()`-shaped code the same way our current `EthereumProvider` does, it doesn't take over `sendTransaction`/`eth_call`. There is also an even lighter framework-agnostic "AppKit Core" (`@reown/appkit-universal-connector`) for non-React usage, but since this is a Next.js/React app, the React + Ethers adapter is the right target, not Core.
2. **Custom EVM chain support:** first-class. A custom network is a plain object (`id`, `chainNamespace: 'evm'`, `caipNetworkId: 'eip155:4663'`, `name`, `nativeCurrency`, `rpcUrls`) passed into adapter config — structurally identical to what `lib/constants.ts`'s `CHAIN` object already holds. Registering chain 4663 is a mechanical config translation, not new engineering.
3. **Connectors:** injected wallets (MetaMask/Rabby/Coinbase/etc. via EIP-6963 auto-discovery — better than our current manual `providers.find(p => p.isRabby...)` sniffing), WalletConnect v2, email/social login, SIWE/SIWX, and smart-account support. We would only use the injected + WalletConnect connectors; email/social login and smart accounts are irrelevant to this app's model (self-custody wallet against a UR/Seaport allowlist) and should stay disabled to avoid scope creep and extra bundle weight.
4. **Pricing (Reown Cloud, fetched today):** Free tier — 500 MAU for embedded-wallet/SIWX features (irrelevant if we don't use them), **2.5M RPC calls/month**, 1 project. Plain WalletConnect-connector usage (what we'd use) is not MAU-metered the way embedded wallets are, so the existing free project ID should comfortably cover current traffic — but confirm actual usage against the 2.5M RPC/month figure before flipping the flag on in production, since AppKit's relay/analytics calls count against it in ways our hand-rolled `EthereumProvider.init()` may not have been using at the same rate.

## Concrete benefits over what we have

- **Deletes an unreproducible 4.75MB binary artifact** and replaces it with versioned, `npm`-installed, patchable packages — this alone is worth doing independent of any UX motivation, because right now a WalletConnect security patch cannot be pulled in without redoing whatever manual bundling process produced that file.
- **EIP-6963 injected-wallet discovery** replaces the current brittle `isRabby`/`isMetaMask`/`isBraveWallet` flag-sniffing in `getEthereumProvider()`/`getInjectedEthereumProvider()` (`lib/wallet.ts:38-75`) with the standard wallet-announcement protocol — fewer "wrong extension picked" bugs.
- **Built-in mobile deep-linking and session persistence** (AppKit's modal handles reconnect-on-reload, QR-vs-deeplink branching, and pairing expiry) — the exact class of bug the concurrent wallet-state-fix agent is chasing (nav shows disconnected while page is connected) is often a session-restore bug, and AppKit's session store is one more option to lean on *after* that fix lands, not a replacement for it.
- Native chain-switch UX prompts (`wallet_addEthereumChain`/`wallet_switchEthereumChain` flows) are handled by AppKit's own UI, which could eventually retire the elaborate manual `need_chain` phase/state machine in `ConnectWalletModal.tsx` (lines 103-138, 183-206) — but that machine exists specifically because Rabby-over-WalletConnect hangs on switch (`ensureRobinhoodChain` in `lib/wallet.ts` races a 3s timeout for exactly this reason). AppKit does not eliminate that underlying wallet-side bug; at best it gives us a nicer shell around the same workaround.
- Is this "mostly branding"? No — the connector-discovery and session-management pieces are real engineering improvements over hand-rolled code. But it is *not* a fix for our actual open bug (shared wallet state / nav-vs-page mismatch); that is being fixed independently and AppKit should not be framed as solving it.

## Concrete costs

- **New dependencies:** `@reown/appkit`, `@reown/appkit-adapter-ethers` (plus their own transitive WalletConnect/relay deps). This is an addition to a codebase that currently has zero WalletConnect packages in `package.json` — evaluate the installed size honestly before committing; AppKit's modal + relay client historically has not been small (it embeds i18n, QR rendering, and multi-wallet UI), so "smaller than 4.75MB" is likely but should be measured, not assumed, once actually installed.
- **Bundle impact on Passenger/standalone deploy:** same lazy-load pattern we use today (`import()` on demand) should be preserved regardless of package choice — this is a code-organization decision, not something AppKit forces either way. Confirm the AppKit chunk stays out of the main bundle and is only pulled when "Connect Wallet" is actually opened.
- **Migration effort:** replacing `lib/wallet-connect.ts`'s `connectWithWalletConnect`/`qrDataUrlForUri`/`cancelWalletConnectConnect` surface with AppKit's hooks/modal touches `ConnectWalletModal.tsx` directly — which the wallet-state-fix agent currently owns. Do not touch either file until that work lands; this evaluation deliberately made no code changes to them.
- **New failure modes:** AppKit owns its own session/reconnect state machine; if it disagrees with app-level state (the same class of bug currently being fixed), we'd be debugging AppKit's session model instead of our own ad hoc `preferredProvider` singleton — not obviously better, just different. AppKit's relay-dependency and email/social-login code paths (if accidentally left enabled in the modal config) would also introduce dependencies (their own OAuth/relay calls) this app has no reason to need.
- **Pricing/quota:** free tier is 2.5M RPC calls/month and unlimited-enough for our WalletConnect-only usage, but this must be watched — AppKit's analytics/relay traffic pattern is not necessarily 1:1 with the current bespoke bundle's call volume.

## Risk to existing safety guarantees — the non-negotiable part

**None of `lib/wallet.ts`'s guarantees are at risk, provided the migration stays scoped to the connector layer.** Concretely:

- `assertSafeSwapDestination`, `simulateTransaction`, the gas-floor logic, and the pre-broadcast chain re-check all operate on the `Eip1193Provider` interface (`{request, on, removeListener}`) returned by `getEthereumProvider()`. AppKit's Ethers adapter exposes exactly this shape (it's how `useAppKitProvider` hands you a provider for `ethers.BrowserProvider`) — nothing in AppKit intercepts or reshapes `eth_call`, `eth_sendTransaction`, or `eth_signTypedData_v4` calls; it only manages *how a provider is obtained and which session it belongs to*.
- The one thing that must be preserved deliberately, not automatically: `getPreferredWalletProvider()`/`setPreferredWalletProvider()` and `isWalletConnectActive()` are load-bearing today — `ensureRobinhoodChain()` uses `isWalletConnectActive()` to pick a 3s vs 12s switch timeout, and the "need_chain" UI flow depends on knowing whether the active session is WalletConnect. Whatever glue code replaces `lib/wallet-connect.ts` must keep exposing an equivalent "is the active provider a WalletConnect session" signal, or the Rabby-hang workaround silently regresses.
- Do not let AppKit's own "Send Transaction" UI actions (if the modal SDK exposes any) replace our `sendTransaction`. Only use AppKit for **connect / session / provider acquisition** and keep every send routed through `lib/wallet.ts`.

## Phased plan (if/when this is picked up — not now)

1. **Phase 0 (now, done by this report):** no code change. Confirm free-tier RPC quota is sufficient once real AppKit relay traffic is measurable, and confirm actual gzipped size of `@reown/appkit + @reown/appkit-adapter-ethers` once installed in an isolated branch.
2. **Phase 1 (after wallet-state-fix and nav work land):** flag-gated proof-of-concept. Add `@reown/appkit` + `@reown/appkit-adapter-ethers` behind a `NEXT_PUBLIC_WALLET_UI=reown` (or similar) flag that is **off by default**. Build a parallel connect path that, when enabled, uses AppKit to acquire a provider and calls the *exact same* `setPreferredWalletProvider`/`isWalletConnectActive` contract `lib/wallet.ts` already expects — so `lib/wallet.ts` needs zero changes. Register chain 4663 via the custom-network object shown above.
3. **Phase 2:** internal dogfood with the flag on for the team only; verify session persistence actually fixes (not just relocates) the "connected in page, disconnected in nav" symptom, verify Rabby chain-switch behavior over AppKit's WalletConnect connector matches or beats the current timeout-and-retry UX, verify bundle size impact on Passenger cold start.
4. **Phase 3:** flip default on, delete `public/wallet-connect-bundle.js` and `lib/wallet-connect.ts`'s custom bundle-loading code, keep the flag for one release as an instant rollback switch, then remove it.
5. **Never in scope:** wagmi, viem, AppKit's embedded-wallet/email-login/SIWE features, or any change to `assertSafeSwapDestination`'s allowlists or `simulateTransaction`'s hard-fail behavior.
