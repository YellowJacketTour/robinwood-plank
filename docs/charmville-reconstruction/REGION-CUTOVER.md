# Joined native region cutover audit

Audited 2026-09-13. **Do not enable the two-screen region in the live quest yet.** This is a source/header audit, not a compiled quest or browser pass. Scope: `Homestead.zs`, its JS transports, native geometry and movement projections. Engine source is `../charmville-references/zquest-classic` at recorded revision `b9354acc0f4bbcfda3b390f98ff5032fbf0f6eb0`; bindings are `../charmville-references/zquest-native-212/runtime/include/bindings`. Browser binary parity is unproven.

## Coordinate contract

`native-atlas.ts` lays out west screen 62 at cell (0,0), meadow screen 63 at cell (32,0), each 32x22 cells of 8px. The candidate region is 512x176px. Meadow local pixels become region pixels by adding (256,0): beds (24,88), (56,88), (88,88) become (280,88), (312,88), (344,88). Spawn (16,72) becomes (272,72).

`native-region.ts` is deliberately unselected. `regionPosition` and `screenPosition` convert point coordinates only; they do not validate a 16x16 actor footprint. `meadowRegion.blocked` contains raw terrain cells. Apply footprint expansion after joining the raw maps, including footprint samples across the seam, before admitting movement. Existing `native-world.ts` does footprint expansion separately per screen and `crossNativeBorder` implements an explicit edge transfer with y cells 4..12, a 100ms bound, destination spawn and epoch increment. A seamless walk is not that transfer protocol. Screen-local actor bounds stop at x240; a body straddling the seam at x248 cannot be represented by merely normalizing HeroScreen/local pixels. A normalization-only adapter can preserve the existing discrete-screen compatibility path, but seamless authoritative admission requires joined footprint geometry and a coherent movement protocol.

The decisive native distinction: `Game->GetCurScreen()` is the origin of the region (62 after joining), while `Game->HeroScreen` tracks the physical screen containing Hero. Hero coordinates are region pixels. Merely changing screen tests to HeroScreen still leaves every coordinate payload wrong unless normalized. Merely extending JS x bounds would persist region pixels under a screen-local geometry identity.

## Available native bindings and cautions

- `Game.zh:409-424`: CurScreen is the origin; HeroScreen is the actual containing screen. `region.zh`: Region ID, Width/Height, ScreenWidth/Height, NumCombos, OriginScreenIndex, RelativeScreenX/Y and WorldOffsetX/Y. `SetRegion(map, origin_screen, width, height, region_id)` writes mapdata RegionID; its map argument is a native map, not a DMap ID. Read the DMap mapping before authoring.
- `Game.zh:1224-1245`: `LoadTempScreen(layer, screen)` targets one loaded region screen; `LoadTempScreenForComboPos(layer,pos)` targets its containing screen. `mapdata.zh:203-205` says a region-wide temporary pointer exposes all combo arrays but singular-screen properties refer to the origin. Do not infer that LayerMap or global Screen metadata refers to meadow.
- `src/zc/maps.h:118-151`: region combo positions are screen-major, 176 per screen. `POS_TO_RPOS`, `COMBOPOS_REGION` and bounded variants are C++ source helpers, not automatically callable ZScript APIs. Use verified header APIs/explicit mapping.
- `screendata.zh:19-46`: DEFAULT changes meaning in regions; REGION uses sprite coordinates; PLAYING_FIELD fixes UI to the field; SCREEN fixes UI to the full screen. `viewport.zh` exposes X/Y, Width/Height, Mode and Target. `src/zc/maps.cpp:370-390` fixes the usual viewport to 256x176 and centers/bounds it. Joining maps does not widen the camera.
- `region.zh:87-101` bundled IncludesScreen helper uses `dx > ScreenWidth` / `dy > ScreenHeight`, allowing equality; do not use this helper alone as admission validation. Explicit destination allowlists and `<` bounds avoid trusting that edge behavior. RelativeScreenX/Y return arithmetic offsets in regions without validating membership.
- `hero.zh:742` exposes Hero->Warp(dmap,screen). Header/source availability must be followed by compile and hosted runtime smoke tests before claims of working support; past unsupported binding calls have aborted this runtime.

## Required proof for cutover

Keep the existing quest/admission path selected until a separate candidate passes: first arrival into each half; rejected correction in meadow and west; seam crossing in both directions with a 16x16 footprint and no fabricated trail samples; reconnect on each half; all three beds with tool/contact/receipt alignment; six followers across the moving camera; cross-seam peer positioning and instance isolation; attack, faint, capture and their acknowledgments; fixed HUD during camera travel; departure and reentry through actual warps. Verify extracted collision after farm preparation on every active layer, confirm west terrain unchanged, and inspect real browser frames at camera-left, middle and right. Tests must assert geometry identity and persisted local/region coordinates, not only rendered pixels. A candidate atlas/unit conversion test is not evidence that the quest is safe to join.
