# One-shot research brief: the fastest, most complete, most accurate live on-chain buy feed for a real-money leaderboard contest

You are being handed this with **zero prior context** about any specific codebase. Treat it as a fresh, first-principles research and design problem. Research broadly, cite real current sources, and design a bespoke, best-imaginable solution — don't just survey.

## The situation, plainly

We run a small ERC-20 token ("$PLANK") on an EVM-compatible L2 ("Robinhood Chain" — real, measured ~9.9 blocks/second, real finality profile: sub-second soft confirmation, ~13 minutes to L1-anchored hard finality). We are running a live, real-money contest: whoever makes the single largest real buy of $PLANK during a ~31-day window wins a real prize. A public leaderboard shows every confirmed buy and the current leader, and is expected to update within seconds to minutes of a real buy happening on-chain.

## What we've already built tonight, in order

1. **First implementation**: polled a third-party REST block explorer (Blockscout) for each of 3 hand-verified canonical liquidity pools' own transfer history, matched individual ERC-20 transfer legs to/from a "recipient" directly. This broke completely: real swaps route through a router/aggregator contract (Universal Router / SwapRouter02 — the overwhelmingly common real-world shape), so the buyer's own wallet never directly touches the pool, and every real buy was misclassified.

2. **Rewrite**: replaced the explorer with direct RPC calls (`eth_getLogs` for the token's own Transfer events filtered to transfers FROM a canonical pool, `eth_getTransactionReceipt` for full per-transaction log detail, `eth_getTransactionByHash` for native-ETH-value-funded swaps). Replaced per-leg matching with **net ERC-20 balance delta computation per address across the whole transaction** — a pass-through router nets to ~0 for itself with no special-casing, so the real buyer/real value-paid resolves correctly regardless of how many hops a real payment took. This fixed the router-attribution problem structurally, confirmed against multiple real, independently-verified production transactions.

3. Along the way, found and fixed several further real bugs the same night: a finality-margin calculation that assumed a hardcoded (and wrong, ~5x too slow) block rate; a review-queue write that never refreshed its own stored reason on re-evaluation (so old, already-fixed misclassifications looked permanently valid); a feedback loop where the fraud pipeline treated its own past (buggy) conclusions about a wallet as independent evidence against that same wallet forever; a shared single RPC provider (no redundancy configured for this chain) that got circuit-breaker-jailed for 15 real minutes by an over-eager backfill script, taking the live watcher down with it; and a wei-to-USD conversion helper that silently truncated any payment under 0.001 ETH (~$2.47 at current prices) down to exactly $0.00.

4. **The system now works** for buys we've tested against — it discovers real candidates, classifies real net payments correctly, and confirms real buys onto the public leaderboard within roughly a 2-minute cron cycle plus the finality delay.

## The problem we cannot yet explain

**We just learned of real buys over $600 and over $1,000 that happened very recently (not during an old backfill gap — recent, real-time activity) that our current live system, which we've directly confirmed IS running continuously and successfully discovering and confirming OTHER real buys right now, still did not catch.** We do not yet know why. Candidate theories, none confirmed:

- A discovery-side gap: maybe these specific transactions used a transaction/routing shape our `eth_getLogs` filter (Transfer events on the token contract, filtered to `from` = one of 3 hardcoded canonical pool addresses) doesn't match — e.g., a different pool/venue entirely, a different token-transfer pattern (a proxy/wrapped-token hop we don't decode), or a genuinely different DEX/aggregator whose settlement doesn't emit a plain Transfer FROM the pool address in the shape we expect.
- A classification-side gap: maybe the transaction IS discovered and reaches our net-balance classifier, but something about its specific shape (a multi-hop route through more than 2 hops, a batched multi-buyer settlement, an intermediate wrapping/unwrapping step) causes our net-balance computation to net out incorrectly and either produce no candidate or attribute the value to the wrong address.
- A timing/cursor gap: our RPC-based scan cursor advances in chunks and only evaluates candidates once they're past a computed finality margin — is there a real, live bug in how the "in progress" scan window and the finality boundary interact that could silently skip a real transaction sitting right at the edge of two scan passes?
- An amount-formatting gap: are we certain a genuinely large real transaction's value doesn't hit some OTHER numeric edge case (e.g., BigInt overflow, a value large enough to behave unexpectedly in a spot we haven't hardened, since we already found and fixed one real numeric truncation bug tonight for very SMALL amounts — is there an analogous, undiscovered bug for very LARGE amounts)?

We are not confident which of these (or something else entirely) is the real cause, and we do not want to keep guessing and patching reactively all night — we've now found and fixed six distinct real bugs this way and want a fundamentally more complete, verified-correct design instead of a seventh patch.

## What we need from you

1. **A definitive, from-first-principles design for "catch every real DEX buy of a specific token on an EVM chain, with no discovery gaps, as fast and cheaply as possible."** Assume you may use: direct RPC log scanning (`eth_getLogs`/`eth_getFilterChanges`/WebSocket `eth_subscribe` for `newHeads`/`logs`), full transaction receipts, call traces (`debug_traceTransaction`/`trace_transaction` where available), the token's own Transfer events, the DEX pools' own native `Swap` events (Uniswap V2/V3-style, and any newer V4/singleton-pool-manager architecture that might apply), and any real third-party indexing/analytics service ecosystem that exists in 2026. For each real technique, be concrete about exactly what it does and does not guarantee to catch, with real citations.

2. **Specifically address large-transaction/batched/aggregator-routed buys.** Is there a real, known class of transaction shape (CoW Swap-style batch settlement, an aggregator like 1inch/0x/Odos doing a multi-hop split across several pools in one call, a MEV-related sandwich/backrun structure, a cross-chain bridge deposit landing as a local mint rather than a pool-originated transfer) that could plausibly explain a large real buy not showing up as a clean "Transfer FROM a known pool address"? What's the real, general (not case-by-case) way to catch these?

3. **Live-feed architecture for sub-minute (ideally sub-10-second) real-time detection.** Is polling `eth_getLogs` on a cron cycle (our current approach, ~2 minutes) meaningfully worse than a live WebSocket subscription (`eth_subscribe("logs", ...)`) for a small-to-medium chain like this? What's the real state of the art for "as close to instant as reasonably possible" DEX buy detection for a single token, at small-team budget/complexity?

4. **A verification/completeness-auditing method we can run ourselves going forward.** Given we've now been burned twice by silent gaps (an old REST-API-based system with unexplained misses, and now a newer RPC-based system that STILL appears to miss some real large buys), what's the real, standard way to continuously verify "did we actually catch everything real that happened" — e.g., periodically cross-checking our own discovered-transaction count/volume against an independent, real source (a DEX analytics API, a subgraph, a block explorer's own aggregate volume stats) and alerting on any material discrepancy, rather than only discovering gaps when a human happens to notice a missing large transaction on a different UI?
