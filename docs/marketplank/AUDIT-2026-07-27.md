# Marketplank security audit — 2026-07-27

Adversarial self-review of everything that can touch user funds: the vault
contract, the Seaport integration, the order relay, and the wallet layer.

**What this is:** a rigorous internal review. Every finding below was
*reproduced with a failing test before being fixed*, and each fix is pinned by
a regression test that fails if the defect returns.

**What this is not:** a substitute for an independent professional audit of
the vault contract before it holds real value. An AI reviewing its own code
shares its own blind spots — that is exactly why the deployment gate in
`SPEC.md` §7 still stands.

## 1. CRITICAL — Selling dust against an empty share reserve drained the pool

`sellShares` computed `ethOut = sharesIn * ethReserve / (shareReserve + sharesIn)`
without checking `shareReserve > 0`. With a zero share reserve the expression
collapses to exactly `ethReserve` **for any input, including 1 wei**.

The state was trivially reachable: the treasury seeds ETH at launch before
anyone has placed shares in the pool. The first person to deposit one NFT could
then take the entire seeded ETH balance for a dust amount of shares.

**Fix:** both reserves must be non-empty; zero-value outputs revert.
**Test:** `FINDING 1` in `test/contracts/VaultDrain.audit.test.ts`.

## 2. CRITICAL — The marketplace could display one price and sign another

The order relay stored client-supplied `priceWei`, `tokenId` and `maker`
alongside the signed Seaport order, and **never checked they agreed**.

Anyone could POST a listing whose card read `0.01 Ξ` while the attached,
genuinely-signed order demanded 100 ETH — or delivered a different token, or
paid an extra recipient. A user who trusted the price on screen and confirmed
in their wallet would have been robbed. No bug in Seaport, no bug in the
vault: purely trusting the client.

**Fix:** structural, not a patch. `lib/market/order-validation.ts` re-derives
every displayed field *from the signed order itself*, so what a user sees and
what they sign are the same object by construction. The API ignores the
client's claims entirely; the buyer's browser independently re-derives the
price before anything reaches the wallet, so even a compromised API or store
cannot mislead them.

Also now rejected: escalating (Dutch) amounts masquerading as fixed prices,
orders paying an unexpected recipient, orders that strip the collection's fee,
and bids that would deliver the NFT to someone other than the bidder.

**Tests:** 11 cases in `test/market/order-validation.test.ts`, including the
headline attack.

## 3. CRITICAL — Redemption minted claims the vault could not honor

Redemption burned one share but *minted* a fee on top, so total share supply
and NFT backing drifted apart on every redemption. Over time this produced
more share-claims than NFTs — the last holders would find nothing to redeem.

**Fix:** redemptions now burn the share **plus** all charges and re-mint only
the charges, so supply moves exactly `-1 share` per `-1 NFT`. The contract
asserts a solvency invariant after every state-changing call:

```
totalSupply() + pendingRedeemCount * SHARE_UNIT == heldTokenIds.length * SHARE_UNIT
```

Any operation that would break it reverts.
**Tests:** `FINDING 2` plus a randomized multi-operation invariant test.

## 4. HIGH — Random redemption could be cherry-picked for free

`redeemRandom()` drew and delivered in one transaction. A contract caller could
inspect which token it received and revert the transaction if it wasn't a rare
one — repeating until it hit a valuable NFT, paying only gas. That drains the
best items from the vault at the plain redeem rate and devalues everyone
else's deposits.

**Fix:** split into commit-reveal. `requestRandomRedeem()` burns the shares and
anchors to the current block; `claimRandomRedeem()` draws from that block's
hash in a later block. The outcome is unconditional — abandoning an unwanted
draw costs the full share.

**Known residual limitation, stated plainly:** block hashes are only available
for 256 blocks, so `refreshRandomRedeem()` exists to stop an honest user's
already-paid-for redemption being stranded if they wait too long. A determined
attacker could use it to reroll — but only by waiting out a *full 256-block
window* each time, paying gas, while the vault's contents change underneath
them. We judged that bounded cost preferable to charging honest users who hit
a network hiccup. It is a real trade-off, not a solved problem.

**Tests:** `FINDING 5`, using a purpose-built attacker contract
(`contracts/test/MockRerollAttacker.sol`) that attempts the same-transaction
draw-and-act and must revert.

## 5. HIGH — A paid-for redemption could be stranded

`redeemTarget` could take the last NFT even when it was the backing for a
pending random redemption whose shares were already burned — leaving that user
with nothing.

**Fix:** `pendingRedeemCount` reserves one NFT per pending claim;
targeted redemption reverts rather than consuming reserved backing.
**Test:** `FINDING 6`.

## 6. HIGH — Offers were denominated in a currency Seaport cannot use

`buildOffer` offered native ETH. Seaport cannot pull ETH from an offerer at
fulfillment time — only ERC-20s work as offer items. Every bid would have
been signable but unfillable: a bidder's wallet would show a valid-looking
offer that silently does nothing forever.

**Fix:** bids are denominated in WETH.

**Address verified by direct RPC call, not assumed:**
`0x0Bd7D308f8E1639FAb988df18A8011f41EAcAD73` — `symbol()` returns `WETH`,
`decimals()` returns 18, verified proxy over Arbitrum's `aeWETH` (which also
confirms Robinhood Chain is an Arbitrum Orbit chain, not OP Stack — the OP
predeploy address `0x4200…0006` has no code here).

**This one is worth dwelling on:** the search for WETH surfaced at least three
impostor contracts on this chain that also report the symbol `WETH` — one with
zero supply, one unverified, one an LP token. The address is therefore
hard-coded with that warning in the comment, and must never be resolved by
symbol lookup. Had we auto-resolved by symbol, bids could have been routed
into a worthless token.

## 7–10. Medium and low

- **Zero-output swaps:** dust input rounded to zero shares out while keeping
  the ETH. Now reverts.
- **Permissionless seeding:** `seedLiquidity()` was open to anyone. Now
  treasury-only. There is deliberately still **no withdrawal path** — pool ETH
  is committed permanently, so holding the treasury key cannot rug the pool.
- **Unbounded storage:** the relay had no caps. Now 5,000 orders total, 100
  per maker, 180-day maximum lifetime.
- **Phantom listings:** anyone could list a token they didn't own. The relay
  now checks `ownerOf` on-chain, failing *open* on RPC error (a node hiccup
  costs a junk row, never a user's funds).

## Reviewed and found sound

- **Seaport itself** — not our code; canonical bytecode, independently audited
  by OpenZeppelin, Trail of Bits and a Code4rena contest, confirmed verified at
  its canonical address on this chain.
- **`lib/wallet.ts`** — the Trade section's hardening holds up: simulate before
  send, Universal Router allowlist, Permit2/token-only approval allowlist,
  chain-ID pinning, balance-delta proof of delivery.
- **Reentrancy** — vault uses `nonReentrant` throughout and updates state
  before external calls.
- **Fee immutability** — vault fees are `immutable`, ceiling-checked at
  construction; there is no admin path to change them post-deploy.

## Deliberately unresolved

- **EIP-712 signature verification at the relay.** Orders with a malformed
  signature are still accepted into the book; they simply fail on-chain,
  costing a would-be buyer gas but never funds. Full server-side Seaport
  digest reconstruction is error-prone and the on-chain check is authoritative.
  Ownership checks already filter most junk.
- **Independent professional audit of the vault.** Unchanged and non-negotiable
  before `MARKET_ENABLED=true`.
- **Legal/compliance review** of the vault as a financial product — outside
  what this review can speak to.
