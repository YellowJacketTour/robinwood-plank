# One-shot research brief: safely backfilling a low-volume EVM event stream on a shared-hosting, no-dedicated-indexer stack

You are being handed this with **zero prior context** about any specific codebase. Treat it as a fresh, first-principles research and design problem. Research broadly, cite real current sources, and design a bespoke, best-imaginable solution for THIS environment's real constraints — don't just survey generic indexer advice.

## The situation, plainly

We run a small NFT vault (buy/sell shares, deposit/redeem NFTs, add/remove liquidity) on an EVM-compatible L2 ("Robinhood Chain" — real, measured ~10 blocks/second). A public, live-traffic ticker shows the vault's own trade history, read on every HTTP request straight from chain logs via `eth_getLogs` (no subgraph, no dedicated indexer, no persistent background worker process — see hosting constraints below).

**Real, already-confirmed root cause of tonight's specific bug**: one of the vault's own batch functions (`depositMany`) does not emit the vault's own `Deposited` event for the tokens it moves — confirmed via the actual `eth_getTransactionReceipt` for a real transaction, not inferred. The only real, on-chain trace of that deposit is the NFT contract's own plain `Transfer(from, vault, tokenId)` log. So we added a second scan, against the NFT contract (not the vault), filtered to `Transfer` logs where `to == vaultAddress`, to recover exactly this class of event.

## What we've already built tonight, in order, and how each attempt failed

1. **First fallback design**: a resume-cursor walk. On first call, walk backward from the current chain head in a bounded number of `eth_getLogs` chunks (12 chunks × 50,000 blocks = 600,000 blocks), then remember the block where the walk stopped as a persisted "cursor," and on every later call only scan forward incrementally from that cursor (cheap, one small window). **This failed live**: the real missing deposit was ~707,000 blocks back — 107,000 blocks past what 12 chunks covered. The walk still marked itself "complete" (its own internal flag only meant "no chunk threw an error," not "reached real historical coverage") and persisted the cursor anyway, which **permanently** skipped the gap — every later call only ever scans forward from that point and structurally can never revisit what the first walk missed.

2. **Second attempt**: raise the chunk budget to 20 chunks (1,000,000 blocks) so a single cold walk would comfortably clear the known 707k-block gap. **This also failed live**, differently: it caused a real, measured 60.34-second response time and a genuine Cloudflare 504 gateway timeout on the live, public endpoint. A fixed chunk count has no ceiling on how long it actually takes — the public RPC endpoint's own per-call latency is variable — so it cannot be tuned to simultaneously guarantee "far enough back" and "fast enough to answer an HTTP request."

3. **Current stopgap (what's live/proposed right now)**: abandoned the resume-cursor idea entirely. Every request now always rescans a fixed, fresh trailing window — 5 days, estimated as ~4.3M blocks from a flat "~10 blocks/sec" measurement, chunked at the same 50,000-block size used elsewhere in this codebase, fetched in batches of 12 concurrent `eth_getLogs` calls so wall-clock time stays bounded by the slowest single batch rather than the sum of all ~87 chunks. Relies on existing dedupe-by-`(txHash, tokenId)` logic to collapse the overlap between repeated scans of the same window. No cursor exists anymore, so nothing can be falsely marked "already covered."

## Real hosting constraints (do not design around infrastructure we don't have)

- **Phusion Passenger on shared cPanel hosting.** Not serverless, not a dedicated always-on process host, not Kubernetes. Passenger spins worker processes up/down; there is no guaranteed long-lived in-memory state between requests.
- **A cPanel cron IS available** and is already used for a separate periodic data-refresh script (runs every 2–15 minutes depending on the job) — so "a lightweight periodic cron job populating a small cache table" is a legitimate, already-proven-workable option, not a hypothetical.
- **PostgreSQL is the only datastore** (no Redis, no external KV service).
- The live HTTP endpoint in question currently sits behind Cloudflare, which appears to enforce something at or near a 60-second proxy read timeout (the 504 above was measured at 60.34s).
- We do not currently know the real, documented `eth_getLogs` range/rate limits of the specific public RPC endpoint we use (Robinhood Chain's own public node) — our working assumption of "50,000 blocks per call is safe" was only ever validated empirically (it hasn't failed yet), never against any published limit for this specific provider.
