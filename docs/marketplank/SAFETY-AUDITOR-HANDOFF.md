# PlankCrash safety candidate — independent auditor handoff

Date: 2026-09-09. Status: implementation and internal adversarial review complete for the changes below; **not approved for mainnet**. This document is an engineering handoff, not an independent audit opinion, a guarantee against loss, or evidence that all repository contracts are safe. The accompanying source snapshot identifies the actual files and compiler inputs. Earlier launch snapshots are superseded for these changes.

## Decision and scope

The implemented emergency control stops **new admission**. It does not give an administrator custody over player funds, a round-cancellation power, an upgrade power, or a way to change a committed outcome. Existing settlement, refund claims, withdrawals and funded ledger delivery remain callable. This separates emergency exposure control from ownership of balances.

The operator surface has two actions: **Freeze** and **Reopen**. Freeze is immediate once included on chain. Reopen first requests governance authorization; its execution is possible only after the immutable delay. The guardian can veto by freezing again. A permissionless keeper can execute a matured authorization, but cannot create that authorization. Wallet/multisig signing remains necessary; “two buttons” does not mean removing governance consent.

The selected graph is PlankGuardedCrash → PlankCrash, PlankCycleLottery → PlankNumberedLottery → PlankLottery, PlankBank, PlankRakeRouter, PlankBurnEngine, PlankV2TwapOracle and the production DrandBeacon dependency. Capped-pool mathematics is included. The repository contains 45 Solidity source files, including test fixtures, marketplace code and experimental alternatives. All current compilation units were scanned, and the repository regression suite ran. Manual safety changes and focused review apply to the selected casino graph. The inventory explicitly distinguishes other contracts; they are not silently certified by inclusion in a passing build.

PlankScalableCrash and experimental live-lock contracts are not the production selection. In particular, the new base-crash recovery changes must not be assumed to exist in the independent scalable implementation. The selected game remains bounded to 256 seats per production round. Billion-user throughput and unconditional autonomous operation are not demonstrated by synthetic arithmetic tests.

## Threat model

Adversaries may split capital among wallets, collude on targets, choose minimum or maximum stakes, submit late or duplicate transactions, observe published entropy, call permissionless settlement with hostile gas limits, operate a reverting smart wallet, reenter through receiving contracts, and withhold keeper service. Administrators may lose keys or act maliciously. Oracle/router/lottery dependencies may revert. RPCs may time out, return stale reads, or be temporarily unavailable. UI displays are not an authority for acceptance or payout.

The contract must not treat an address count as proof of unique humans. Coalition analysis aggregates controlled stake, fees and subsidies across the coalition, including its expected lottery reward. Splitting a stake must not create a free funded claim or multiply an allocation. A bigger historical ledger is not evidence of spendable wealth: obligations, protected principal and distributable balances must be distinguished.

Assumptions still required are chain execution and eventual transaction inclusion, sound deployed bytecode and cryptography, correctly pinned randomness verification, secure user keys, correctly configured immutable sinks, enough gas to progress, and accessible signing/recovery arrangements for governance. No smart contract can return funds to a person who has irrecoverably lost all authorization, or execute during an indefinitely halted chain. “Never drained” and “never stranded” cannot be unconditional promises.

## Authority matrix

| Actor | Freeze admission | Authorize reopen | Execute matured reopen | Take another user's credit | Cancel a chosen losing round |
|---|---|---|---|---|---|
| Guardian | Yes | No | Yes, like anyone | No | No |
| Safety governance | Yes | Yes | Yes | No | No |
| Keeper / public caller | No | No | Yes | No | No |
| Player root wallet | No | No | Yes | Own balance only | No |
| Bank session key | No | No | Yes | Cannot redirect root withdrawals | No |

Guardian and governance addresses are distinct, nonzero and immutable. The delay is constrained to one hour through seven days. Production defaults to one day; the local test fixture uses one hour. Production deployment requires contract code at both role addresses. This is a minimum check, not verification of multisig owners, threshold, modules, guards, recovery or upgrade behavior. Those must be reviewed independently. A guardian can keep admissions closed indefinitely; that availability power does not include stopping existing claims.

OpenZeppelin describes timelocks as a way to constrain administrator actions and give users time to respond. It also explains why role design itself is a security boundary. The implementation uses the repository's pinned OpenZeppelin 4.9.6 primitives; current 5.x documentation is design guidance, not a claim that dependencies were upgraded. [OpenZeppelin access control](https://docs.openzeppelin.com/contracts/5.x/access-control), [4.x security API](https://docs.openzeppelin.com/contracts/4.x/api/security).

## Findings repaired in this candidate

**S-01 — recovery coupled to next-round scheduling.** Settlement, voiding or timeout refund previously also required successfully scheduling the following round. A broken beacon schedule could roll back the preceding accounting transaction. Final accounting now attempts the next start through a self-only isolated call with a bounded gas budget. On failure, RoundStartDeferred is emitted and the current terminal round remains terminal. Anyone can call restartRounds when the dependency recovers. Claims do not require a successful restart. The constructor still requires an initial valid schedule, avoiding deployment of an unusable first round.

**S-02 — missing narrow admission circuit breaker.** PlankGuardedCrash introduces the role and delay policy above. The base private admission path invokes the hook before accepting a seat. This covers direct ETH, round-bound entry, bank root entry and bank session entry. Tests show a paused bank entry rolls back both balance debit and session spending. Already committed positions are not changed by a freeze, avoiding a guardian-controlled adverse-outcome cancellation option.

**S-03 — rejecting recipients could not choose another exit.** Crash, bank and lottery now provide root-authorized withdrawTo methods. They debit only the caller's ledger, reject the zero address, apply checks-effects-interactions and nonReentrant, and roll back the debit if the transfer fails. A bank session cannot use this method to withdraw its owner's funds. A smart wallet still needs a functioning authenticated execution method; this is not recovery from total key loss or an irreparably broken wallet contract.

**S-04 — impractical timeout defaults and dependency-sensitive recovery.** The old deployment default was 30 days, which combined with the abandoned-round multiplier of 30 to create a 900-day final fallback. Production default is now one hour, constrained by deployment checks to one through 24 hours. Abandonment remains 30 times the chosen timeout: 30 hours at the default. After abandonment the keeper attempts settlement first, then refund without first requiring a healthy beacon read. An adversarial test breaks both beacon read and scheduling and verifies refund, withdrawal and later restart.

This repair has a tradeoff, not a free security theorem. After sufficiently long censorship or infrastructure failure, refund availability can conflict with enforcing an already knowable losing outcome. The contract permits its terminal settlement/refund race after the abandonment boundary. The chosen timeout needs independent review against the target chain's availability and the incentives of the largest possible coalition.

**S-05 — low-gas draw skipping after decoupling scheduling.** The isolated-start repair removed an incidental gas dependency that earlier starvation regressions relied on. Settlement now explicitly requires at least 1.6 million gas remaining before allocating one million gas to the lottery record call. Adversarial low-gas settlement tests pass. The one-million draw budget and 400,000 next-start budget are code commitments and must be measured against every selected runtime at maximum practical storage cost. They are not assumed suitable for an arbitrary upgraded dependency.

**S-06 — incomplete operational parity.** Local and production selection now use PlankGuardedCrash. The older testnet setup has been updated to require distinct explicit guardian/governance addresses, select the guarded contract, use a 30-second admission window and one-hour timeout, and pass the funded-cycle lottery's constructor parameters. That script still intentionally uses a permissionless randomness mock and mock liquidity contracts. It is a mechanics fixture, not a fair public-money environment or production beacon rehearsal.

The public game reads the pause state and blocks admission while paused. The safety page verifies chain identity and prepares a multisig transaction when the connected account is not itself the authorized role. The exact authorized local wallet path was exercised; production multisig integration has not been certified. Safe warns that a faulty guard can itself block transactions, which is why adding arbitrary guard layers without a tested recovery path would be counterproductive. [Safe guard guidance](https://docs.safe.global/reference-smart-account/guards/setModuleGuard).

## Accounting properties and economic boundaries

For each contract, native balance must cover its explicit accounted liabilities. Crash accounting distinguishes player credits, current stake escrow, routed allocations, spendable reserves and protected principal. Lottery accounting distinguishes banked prize, credited winnings, founder escrow and provisioned rollover fees. Bank accounting tracks user deposits. A transfer must reduce exactly the liability it fulfills. Failed delivery must restore the obligation; it must not fabricate spendable surplus. Forced ETH can make actual balance exceed accounting, but must not turn into an unauthorized sweep right.

For player i, promised target return is stake_i multiplied by target_i in basis points with the specified integer rounding. Real settlement is capped by the funded survivor allocation. A displayed target is not a guarantee of receiving that exact multiple when the funded-share rule binds. Returned multiple is actual payout divided by original stake; profit ROI is that multiple minus one. Thus 2x returned means +100% profit, not +200%. Funding docs and player terms must preserve this distinction.

At aggregate level, total fulfilled credits and retained obligations cannot exceed actual received funds. A protected ledger cannot simultaneously remain unspent and fund current payouts. Past rake can increase an endowment and separately provision future subsidies, but repeated transfers among players do not generate external positive-sum wealth. More attendees do not automatically imply more aggregate stake. Guarantees about improving future rounds must be stated against defined funding and payout caps, not wallet counts or historical volume alone.

Lottery selection remains pro rata by stake for that round, independent of how the holder divides it among addresses, subject to documented integer rounding. The numbered machine represents the committed draw range; it must not imply that an illustrative subset of rendered balls changes the actual probability. Each player's hit probability combines the common draw probability with their stake share. The economic outflow budget includes winner payment and the fee on a winning retained seed. Unsuccessful-draw fees are recognized only from funding provisioned for that purpose; an unfunded repeat cannot keep taxing the banked prize.

These properties are exercised by existing capped-pool, coalition, rounding, numbered-lottery, funding and lifecycle regressions. Passing examples do not establish a proof over all EVM traces. An independent mathematics review must bind the final deployed parameters and compare its own implementation with the on-chain formula, including every floor, maximum input and zero case. OWASP's current SCSVS explicitly separates economic logic, authorization and availability controls; all three are necessary here. [OWASP SCSVS](https://scs.owasp.org/SCSVS/), [review checklists](https://scs.owasp.org/checklists/).

## Automation and limits of fail-safe operation

The keeper remains gas-only and permissionless. It progresses normal lock, relay, settlement and delivery; retries deferred next-round start; tries settlement before abandoned refund; and executes a reopening only after governance has already committed it and its delay has elapsed. RPC requests and receipt waits have time bounds. Production relay configuration requires a pinned drand chain hash and at least two relay URLs. None of those URLs acquires authority to change the accepted randomness proof.

Pinning requests and avoiding outcome-dependent cancellation are established randomness security principles. Chainlink's VRF security guidance is relevant as a threat-model comparison, although this game uses drand, not Chainlink VRF. Its guidance cannot substitute for reviewing the actual drand verifier, domain separation, target-round selection and proof binding. [VRF security considerations](https://docs.chain.link/vrf/v2-5/security).

Production still needs redundant independently operated keepers, gas-balance alerts, transaction replacement/nonce recovery procedures, RPC failover, telemetry for deferred starts and failed lottery records, and a tested incident runbook. A single local continuously running process is not evidence of those deployments. No automatic reopening approval, unrestricted guardian bot or external infrastructure deployment was performed in this pass.

The burner uses a TWAP and reserve constraints. A TWAP is not an unmanipulable price oracle: manipulation cost depends on liquidity and the observation interval, and degraded markets or congestion change that cost. A timestamp modulo operation in the TWAP is clock-wrap arithmetic, not a pseudorandom draw. Independent reviewers must check venue identity, liquidity floors, windows and sandwich/economic assumptions on the selected chain. [Uniswap V2 oracle documentation](https://developers.uniswap.org/docs/protocols/v2/concepts/oracles).

## Unresolved release conditions

1. **Permanent dependency failure still cannot be magically repaired.** The forensic extension now stores a failed draw's original seed, round and rake, blocks the next round, and retries it permissionlessly. No subsequent draw can consume its committed board. Its eventual credited winner amount is unchanged by intervening funding. If immutable lottery code is permanently incapable of executing, its obligation remains pending and new games remain stopped; there is no administrator replacement-outcome or sweep power. Crash withdrawals remain available. This is materially stronger recovery, not a guarantee that broken immutable code can always be repaired.
2. **Protected principal is accounting segregation inside the crash contract.** It is not a physically independent minimal endowment contract. An admission pause cannot stop a hypothetical vulnerability in already-open withdrawals. A withdrawal freeze would reduce that exposure but would contradict unconditional exit availability. Stronger physical loss containment would require a separate reviewed vault and narrowly budgeted release interface, not just another frontend button.
3. **Known-entropy abandonment is a liveness/fairness tradeoff.** Review the timeout and settlement/refund race under prolonged censorship. The keeper's settlement-first policy does not constrain malicious callers.
4. **Immutable dependencies can remain unavailable.** Permanently broken founder sinks, router or lottery code can strand their own escrows. There is intentionally no administrator sweep. Alternate player recipients do not fix unrelated sink obligations.
5. **Production governance and real-beacon evidence remain outstanding.** Review multisig setup, role recovery, chain-specific gas, incident drills and a real-beacon public-testnet soak bound to the final source/configuration. Mock-beacon browser success is insufficient.
6. **All scanner findings are not independently cleared, and the source is not formally verified.** The external auditor must resolve the selected graph and separately review any other contracts intended for deployment. No existing deployed immutable contract is retroactively fixed by changing this repository.

Solidity's security guidance recommends bounded execution, checks-effects-interactions, pull-based flows, fail-safe design and peer review. These repairs follow those principles, while the unresolved conditions prevent using them as absolute marketing promises. [Solidity security considerations](https://docs.soliditylang.org/en/latest/security-considerations.html).

## Forensic extension: passes, findings and feature coverage

This extension was requested after the initial safety pass. It traversed the selected crash, bank, lottery, router, burner, oracle and beacon source bodies and their call boundaries; followed browser signing and session flows; and reran adversarial, integration and deployment checks. It is not a claim that every marketplace route, experimental branch, dependency or line in the entire website received an independent manual audit. The machine-readable inventory lists all 45 Solidity files with line counts and hashes, so coverage cannot be confused with a blanket certification.

### Additional repaired findings

**F-01 — lost lottery obligations after a transient failure.** pendingLotteryRound and its original seed/rake now survive settlement failure of the lottery call. The next book cannot start while that commitment is pending. retryLottery reuses those exact arguments; failed retries revert without erasing them; successful delivery clears the commitment and attempts restart. It is nonReentrant and preserves the explicit draw gas budget. The keeper checks pending recovery before restarting. The browser leaves an unrecorded Draw queued and does not deliberately restart its already-shown flight. The regression forces a winning original draw, interrupts the lottery, adds later funding, withdraws crash winnings, recovers through the keeper while frozen, verifies the original lottery payment, withdraws it to another recipient and rejects a second retry.

**F-02 — liquidity could disappear between price updates.** consult now checks current reserves against the immutable depth floor even when its average is fresh. The regression removes liquidity after priming, then verifies that a burn reverts without spending engine ETH. This stops use of a clearly underfunded venue; it does not establish that a well-funded venue cannot be manipulated across a longer period.

**F-03 — irreparable burner configuration.** The constructor rejects a zero maximum burn size, codeless dependencies, or a TWAP whose token pair does not match WETH/PLANK. Maximum trade size remains a per-call bound, not an hourly spending budget: many permissionless calls can execute in succession. The pool only receives its explicitly routed burn allocation; an independent venue review remains necessary.

**F-04 — deployment-key publication path.** The testnet deployment script previously serialized process.env.DEPLOYER_PK as simulateKey into a manifest intended for public serving. That assignment has been removed and regression-pinned. No corresponding ignored testnet manifest was present locally at inspection. This does not prove that no copy was previously published; if one was, the key must be treated as exposed and any accounts using it investigated. The script now expects testers to connect their own wallet. A production-grade free public test faucet/relay remains a separate required delivery; a shared deployment key is not a solution.

**F-05 — unsafe browser session funding and revocation handling.** The older instant-play flow sent 0.25 ETH to a browser-held key, granted a cap of 100 times the deposit, and could discard local session state even if revocation failed. Entry and automatic restoration of that flow are now restricted to loopback practice mode; the cap is the deposit itself, and failed revocation is surfaced before clearing the key. Normal round-bound root-wallet wagers remain available. Real-money gas-sponsored/session play is disabled pending a separate reviewed design for funding quotes, storage, expiry, recovery and transaction sponsorship. Disabling an unsafe optional feature is intentional; it is not presented as a fully implemented mainnet session system.
