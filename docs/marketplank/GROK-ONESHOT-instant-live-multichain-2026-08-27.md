## 1. What this product is

**Marketplank** (brand: RobinWood, ticker $PLANK), live at `plank.tanggang.life` (production) with `plank.love` pending a hostname cutover. An NFT marketplace aggregating listings/offers/floor/volume/rarity across many chains — Ethereum, Base, Polygon, Arbitrum, BNB, Optimism, Avalanche, zkSync, Solana, Bitcoin (Ordinals), and the project's own "Robinhood Chain" L2 — with a `/market/multichain` home page (a "shotgun view": one page load renders rankings across every chain simultaneously, up to 100 rows per chain, plus trending/movers rails) and per-collection detail pages showing live floor/listings/traits/rarity.

The whole point of the product, in the owner's words tonight, watching it work: they want to click into a barely-synced collection and watch its "archive depth" bar visibly race to 100% in real time — "melt to 100%" was the exact phrase — the way it apparently once did. Whether "instant" is achievable at all, and how, is the open question.

## 2. Current architecture (as of tonight, all real, all read from the actual code — verify against `lib/market/multichain/` before trusting any of this, code moves)

Read `docs/marketplank/SPEC-SYNC-MESH.md` first — it's this repo's own living constitution for the sync mesh and is more authoritative than this document for anything that conflicts.

**The scheduler**: `scripts/mesh-tick.ts` runs continuously (as a long-lived process, not a quick per-tick script — it keeps its own internal worker pool alive until the queue drains, which under real load can be a very long time), claiming jobs from a Postgres-backed queue (`plank_data_jobs`, `lib/market/multichain/control-plane.ts`) and spawning `scripts/mesh-lane.ts` child processes (or running "light" sources in-process) per job. `--limit=N` bounds total concurrent lanes; a separate semaphore additionally bounds OpenSea-touching lanes specifically.

**Demand-priority**: viewing a page (or the rankings page's own continuous "here's what's visible" broadcast, `components/market/GlobalMarketHub.tsx`) POSTs to `/api/market/multichain/visibility-demand`, which calls `prioritizeVisibleCollections` (`lib/market/multichain/collection-demand.ts`) to enqueue/reprioritize real jobs for what's actually on screen. Priority tiers run from background sweep (lowest) through detail-page-click through viewport-visible (highest, with an aging boost the longer something sits visible-but-stale).

**Data sources, per chain type**:
- **EVM chains**: HyperSync (Envio) — real-time on-chain log scanning, no documented hard rate ceiling — is meant to be the primary membership source (promoted 2026-08-26), with OpenSea's REST API as a secondary/fallback source for listings/stats/enrichment. Metadata/traits are resolved on-chain (`tokenURI` via a real Multicall3 batch call, up to 40 tokens/call) then through IPFS/HTTP — **OpenSea's own metadata API is only a last-resort catch-fallback if the on-chain/IPFS path throws**, not the primary path. This part is already well-architected; verify it's still true when you read the code, don't assume.
- **Solana**: Helius (DAS API + RPC) for membership/metadata, Magic Eden for listings.
- **Bitcoin (Ordinals)**: UniSat for membership/listings/rarity.
- **Robinhood's own L2**: OpenSea-only — HyperSync (Envio) has *no chain-ID mapping for it at all*; it's a private/custom chain their public indexing infrastructure doesn't cover. This is a real, currently-unsolved gap for that one chain specifically.

**Provider capacity** (verify these numbers live before acting on them — they were true as of tonight, not guaranteed true when you read this):
- OpenSea: 600 requests/hour *per API key*, real, documented. The app has 7 real keys pooled (`lib/market/multichain/discovery/opensea-key-pool.ts`), load-balanced. **Unresolved, important question**: a real 429 from OpenSea causes the app to jail the entire *account-wide source name* ("opensea-stats", "opensea-membership"), blocking every key in the pool simultaneously for a fixed 20-minute cooldown — a deliberate, already-shipped design choice, with the code comment stating explicitly "a jailed account blocks every key in it, not just one." This implies whoever wrote that fix believed OpenSea enforces some real limit at the *account* level, not purely per-key-string. **If that's true, having 7 key strings may only provide redundancy/load-distribution, not real 7x throughput**, because they might all draw against one real account-level ceiling. This was never verified against OpenSea's actual current documentation or real account structure tonight. **Research this first** — it changes whether "get more OpenSea keys" is even a lever worth pulling.
- HyperSync (Envio): single account, single API token, no multi-key pool exists in this codebase at all (unlike OpenSea/Alchemy/Helius, which all have `*-key-pool.ts` files). No documented numeric rate limit found in-repo — the code only pattern-matches error text for "rate limit/quota/429" to detect it reactively. Envio's real, current published limits (free tier vs paid tiers) were not checked live tonight — check them now.
- Alchemy: also single, unpooled `ALCHEMY_API_KEY`, used for the on-chain `tokenURI` multicall path. A **live, current** code comment (`rarity-index-runner.ts`) explicitly notes real monthly-CU-quota exhaustion has already happened. 30M CU/month free tier. No pool.
- Helius: 4 keys, genuinely pooled and independently jailed (confirmed correct behavior tonight — when this one broke, each key's cooldown timer was different, proving real per-key independence, unlike OpenSea's identical-down-to-the-millisecond jail timers across all 7 keys).

**Local infrastructure**: a genuinely severe, non-obvious bug was found and fixed tonight completely outside the application code — the local dev Postgres instance (self-hosted, `postgresql.conf`) was running the *stock, un-tuned* `shared_buffers=128MB` default against a real ~19.4-million-row, 16GB table (`plank_collection_tokens`), on real SSD storage still configured with the spinning-disk-tuned `random_page_cost=4.0` default. Every single hydration-completion check was silently hitting disk. Fixing this (`shared_buffers=4GB`, `random_page_cost=1.1`, etc.) took a single-collection completeness check from 715ms-1.47s down to 7-28ms — a ~100x improvement, and it had been silently degrading *everything* the whole session before it was found. **This is the single highest-leverage finding of the whole night and it wasn't in the application code at all.** Production runs on cPanel-managed shared hosting with `PGPOOL_MAX=4` (a connection-count limit, not the same knob) — its real server-level tuning is unknown and likely uncontrollable from this app; this is a genuinely open question for production specifically.

## 3. Concrete bugs found and fixed tonight (for context on what's already been tried — do not re-propose these as if they're undiscovered)

All merged to `dev` branch, robinwood-plank repo, `YellowJacketTour/robinwood-plank`, PRs #255-261 plus one direct docs commit:
1. Per-supervisor singleton lock + PID/start-time fingerprinting (prevents duplicate local dev process launches).
2. OpenSea concurrency semaphore scaled to real key-pool size (was hardcoded for 1-2 keys, pool has grown to 7).
3. Per-chain demand rate-limit scoping (was one shared 30/min budget across every visible chain on one page load, instead of per-chain).
4. Job-claim fairness: tie-break by attempt count, not just priority/insertion-order — a perpetually-retrying job with a low database row ID was winning every tie against a never-yet-tried job at the same priority tier, forever. This was the single fix that actually let HyperSync's fast path start running at all.
5. Postgres deadlock retry (real deadlocks started appearing once real concurrency increased; now retried automatically instead of hard-failing).
6. Membership completion is now judged by real aggregate row count vs. real known total supply, not by any one source's own internal "am I done" flag — previously, if HyperSync fully populated a collection through one path, OpenSea's own walk had no way to know and kept re-scanning forever. Extended to Bitcoin/Solana too, not just EVM.
7. The demand-signal request handler's per-key loop was fully sequential (up to 50 keys, each doing 5-8 database round trips, none overlapping) — parallelized.
8. The Postgres tuning above (§2).
9. Multiple supervisor process deaths with no code-level explanation — likely a Windows/Git-Bash process-detachment quirk, not a code bug — mitigated with a recurring watchdog re-launch rather than root-caused (the *why* of the OS-level process death was never actually found).

## 5. What "prove 100% functionality" should actually mean

Total, permanent elimination of every wait state is not physically possible while this app depends on third-party services with real, external, server-enforced rate limits — no amount of client-side cleverness removes a vendor's own ceiling. What *is* achievable, and what you should treat as the real bar:
- Zero *wasted* attempts (a job should never retry against a resource that's known-jailed, known-exhausted, or already proven complete by another source).
- Zero *starvation* (every real piece of work gets a fair, bounded-wait-time shot, regardless of how much other work exists).
- Maximum real utilization of whatever legitimate capacity actually exists at any given moment, across every available source simultaneously, chosen by real-time cost/speed/limit awareness rather than a fixed fallback order.
- Complete, honest, real-time visibility into current state (jailed/healthy/degraded per provider, real backlog depth, real ETA) — never a fabricated "100%" that isn't backed by a real row count matching a real known total supply.

Build and prove *that* bar, with real before/after measurements the way tonight's fixes were each verified live (not just claimed) — and then write up, with real citations, whichever of the open questions in §4 turn out to have real, actionable answers. If an answer requires the owner to do something only they can do (buy a paid HyperSync tier, get more OpenSea partner keys, provision a dedicated RPC node), say so explicitly and give them the real cost/steps, don't quietly work around it.
