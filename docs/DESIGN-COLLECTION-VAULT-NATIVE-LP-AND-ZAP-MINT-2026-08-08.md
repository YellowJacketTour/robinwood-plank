## Part 2 — Grounded, cited external research (new to this document only)

**1. "Seed a permanently-locked liquidity floor, then open the SAME pool to permissionless community add/remove" — is this a named pattern?**

This is most directly the mechanism popularized as **protocol-owned liquidity bootstrapping paired with an open pool**, distinct from pure POL (which never opens to third parties). The clearest real-world precedent for "floor locked forever + permissionless top-up on the identical pool" is:
- **Uniswap v2's own liquidity-lock convention**: projects send their initial LP tokens to `0x000...dEaD` (burn) or a timelock, then leave the *same* pool address open for anyone to add/remove liquidity against — the locked LP tokens simply never get withdrawn, permanently backing a floor of depth. This is an extremely widely used, informally-named pattern ("burned LP" / "locked liquidity") rather than a single canonical protocol, documented across launchpad tooling (e.g. Unicrypt/Team.Finance-style LP lockers, which exist specifically to timelock/burn LP tokens for exactly this floor-then-open shape).
- **Olympus DAO's "Protocol Owned Liquidity" (2021)** is the more commonly cited named coinage for protocol-owned liquidity philosophy generally (OHM bonding to acquire and hold its own LP permanently) — but Olympus's own POL was NOT opened to permissionless third-party add/remove on the same position; it was pure protocol custody. It established the vocabulary ("POL") this repo's own code comments already use (`CollectionVault.sol:44` "protocol-owned... growth", `CollectionLpRenounceAdapter.sol:67-83` "POL non-withdrawable"), but is not itself an example of the specific floor+open-community-layer hybrid asked about.
- The closest fully-matching named launchpad pattern is what several 2023–2025 fair-launch tools describe as **"seeded liquidity with burned LP + open pool"**: the deployer seeds an AMM pool, immediately burns/locks the LP receipt, and the pool then behaves as an ordinary permissionless AMM pool for everyone else — this is the standard "renounce liquidity" claim seen across pump.fun-style and earlier ERC20 launch tooling. This repo's own prior research (already settled per the task's exclusion list) covers pump.fun/launchpad mechanics in `docs/RESEARCH-profit-leaders-2026-07.md` in the sibling `the-exchange` repo per this session's memory — cited here only as an existing cross-repo precedent this user's own work already established, not re-derived.

Net: the pattern the task asks about — permanent floor + genuinely open top-up on the exact same pool — is a known, informally-named DeFi convention ("locked/burned LP + open AMM") rather than a single named protocol; it is NOT the same thing as this repo's current `donateReserves`, which never mints ANY LP position (locked or otherwise) to donors, and never opens a balanced-add/remove path at all (§2 of Part 1).

**2. Real-world zap implementations and their defended risk classes**

- **Balancer's batch-swap + join**: a "zap" in Balancer's ecosystem composes a `batchSwap` (routing an arbitrary input token through one or more pools) with a subsequent `joinPool` call in the same transaction, so a user can go from one token to a BPT (pool token) position atomically. Balancer's own periphery contracts (e.g. `BalancerRelayer`) chain these calls; the user sets `minAmountsOut`/`minBPTOut` bounds on each leg.
- **Zapper.fi-style single-asset-to-LP**: the canonical DeFi "zap" pattern — swap half the input asset for the other pool asset via an AMM, then add both halves as a balanced two-sided LP deposit, minting the LP token in one user-facing transaction. This is exactly the pattern this repo's OWN sibling contract (`robinwood-plank/.claude/worktrees/.../GlobalIndexVault.sol:94-96`, cited in Part 1 §3) explicitly argues against for its own context, calling out that "a zap pays price impact twice and is worst precisely at small size" — i.e. the swap-half leg incurs slippage/impact BEFORE the LP-add leg's own impact, compounding cost for small depositors.
- **1inch/Paraswap-style routing into a basket deposit**: aggregator-routed zaps split/route the input across multiple DEXes to minimize price impact on the swap leg(s), then feed the routed output into the deposit function; this generalizes the two-asset zap to N-asset baskets (relevant to an index-basket zap-mint), at the cost of needing either an on-chain path-finding oracle/router or an off-chain-computed, on-chain-verified route.
- **Known risk classes a real implementation must defend against** (standard, widely documented across all three patterns above):
  - **Slippage on the internal swap leg(s)**: the swap that converts the single input asset into basket-matching assets is itself an AMM trade and can be sandwiched or simply move price against the zapper before the second leg executes; defenses are per-leg `minOut` bounds plus an overall `minSharesOut`/`minBPTOut` on the FINAL output, never trusting intermediate nominal amounts (this repo's own `_pullCredited`/observed-balance-delta discipline, already used throughout `CollectionVault.sol` and the Diamond facets read in Part 1, is a directly applicable existing pattern for this).
  - **Sandwich/MEV exposure**: because a zap is inherently multi-hop (swap + swap + ... + deposit) in one transaction, it is a higher-value MEV target than a single swap — front-run the swap leg(s), let the zap execute at worse pricing, back-run to capture the spread. Standard defenses: tight `minOut` per leg (at the cost of higher revert risk in volatile conditions), same-block quiescence guards (this repo already has `_requirePoolQuiescent()`/`_requireCapNotWorsened` precedent in `IndexTradeFacet.mintSingleAsset`, `contracts/diamond/facets/IndexTradeFacet.sol:53,88`), and/or private mempool submission (off-chain, not enforceable by the contract itself).
  - **Price-impact-paid-twice**: as this repo's own sibling contract already documents (§2 citation above), a naive half-swap zap pays impact on the swap leg AND (implicitly) prices the deposit leg off a post-impact ratio — worst for small deposits relative to pool depth. Balancer-style batch routing across multiple pools, or restricting the zap to assets already reasonably deep relative to deposit size, are the standard mitigations; neither eliminates the cost, they only bound it.

**3. 2025–2026 pattern for bootstrapping liquidity across MANY small long-tail pools — NFTX/Fractional/Tessera**

- **NFTX (the explicit precedent this repo's own ONESHOT doc names itself against/alongside — `docs/ONESHOT-OPUS-AXIOM-1-BULLISH-DELIVERY.md:31`, "NFTX V1 D2... maintained")**: NFTX's vTokens (1:1 NFT-backed ERC20 per collection) are the direct structural ancestor of this repo's own `CollectionVault` vToken. NFTX's own liquidity bootstrap historically relied on protocol-seeded pools per vault plus permissionless SushiSwap/Uniswap pools trading the vToken — i.e., liquidity for each of many long-tail collections was NOT deeply protocol-managed per-pool at genesis; it emerged organically once a vToken existed, with NFTX itself focusing on the mint/redeem (NFT↔vToken) mechanism as the reliable floor rather than guaranteeing deep AMM liquidity for every collection.
- **Fractional.art / Tessera (formerly Fractional)**: fractionalized a SINGLE NFT (or small curated set) into ERC20 shares per vault, rather than pooling an entire collection — liquidity bootstrapping was consequently a per-vault, often thin, problem; Tessera's later pivot toward "modules" (including an AMM/buyout module) reflected the same long-tail-liquidity difficulty: many small vaults, each needing its own market, with no single deep pool to amortize across.
- **The common 2025–2026-era answer across NFT-fragmentation/index protocols to "many small long-tail pools"** is a two-part pattern this repo's own already-built code (independent of this new design) is structurally consistent with: (a) a **weighted meta-index that aggregates exposure across the long tail** so end-user liquidity concentrates in ONE deep index-coin/WETH pool rather than needing N deep per-collection pools (this is exactly what this repo's `IndexCoinPool.sol` + `WeightModule.sol` already do, per Part 1 §2/§5), while (b) each underlying long-tail pool only needs to be "deep enough for the index's own rebalancing flow" (the Energy Bus's Pipe I/L buying pressure, Part 1 §4) rather than deep enough for organic retail volume on its own. This is the same "aggregate the long tail, let one deep pool carry retail liquidity" shape NFTX's own D2 vaults-of-vaults pattern converged toward, and is the load-bearing justification (see Part 3 below) for why this design proposes opening COMMUNITY liquidity on `CollectionVault` pools specifically to deepen the Bus's OWN rebalancing flow, not primarily to compete with the index pool for retail volume.

### 3.1 Real community LP on `CollectionVault`

**Problem, precisely stated from Part 1**: today's pool (`CollectionVault.sol:172-419`) has depth that only grows from (a) treasury's pre-open seed, (b) trading fees compounding into reserves, and (c) permissionless single-sided donation with no LP receipt (`donateReserves`). There is no way for a third party to earn a durable, redeemable claim on the pool's OWN swap-fee flow beyond what they get by simply holding vToken already (since vToken itself IS the only claim that exists, per the contract's own header).

**Proposed shape — a genuinely new LP-token layer ADDED ALONGSIDE, not replacing, the existing pool:**

A new per-vault contract, `CollectionVaultLP` (name NOT YET DECIDED, working name only), that:
1. At the SAME `openPool` moment (or shortly after — see NOT YET DECIDED below), the vault's `treasury` seeds a `permanentFloorShares` amount of LP position into this new contract and — critically — that specific LP position is minted directly to a burn address (`address(0xdead)`, matching the existing precedent this repo already uses for `SEED_LOCK_ADDR` per `IndexBuybackFacet.sol`'s reuse of the same lock address, Part 1 §6) rather than ever being held by `treasury`. This is the "permanently-locked protocol floor" — structurally identical to the "burned LP" pattern documented in Part 2 §1, NOT identical to today's `donateReserves` (which mints nothing at all, vs. this proposal which mints a real, permanently-dead LP position).
2. AFTER the floor is locked, `CollectionVaultLP.addLiquidity(paymentIn, sharesIn)` becomes permissionless: anyone deposits a balanced pair (payment token + vToken, priced at the CURRENT `paymentReserve:shareReserve` ratio the way any constant-product LP-add is priced) and receives a proportional LP-token minted by `CollectionVaultLP` itself — a NEW ERC20, distinct from the vault's own vToken.
3. `removeLiquidity(lpIn)` burns the caller's LP token and returns their proportional share of `paymentReserve`/`shareReserve` — this is the piece that is categorically absent today (Part 1 §2's "no removal path exists at all").
4. Every swap fee already flowing into `paymentReserve`/`shareReserve` via `buyShares`/`sellShares` (Part 1 §2, `CollectionVault.sol:356-408`) continues to deepen `k` exactly as today; LP-token holders now have a REAL, redeemable claim on that growth proportional to their share of `CollectionVaultLP`'s supply, which non-LP vToken holders (who only hold the vToken side) do not get — this is the "real fee-earning" requirement.

**Where this sits relative to `CollectionVault.sol` itself**: this design deliberately does NOT propose modifying `CollectionVault.sol`'s existing reserve variables or fee-routing logic (`_routeStreamA`, `_swapFeeSinkCut`, all read in Part 1 §2/§4) — a new external contract references the vault's `paymentReserve()`/`shareReserve()` (both already public state, `CollectionVault.sol:172-173`) and the vault's own `buyShares`/`sellShares` are UNCHANGED. This keeps the "no `.sol` file touched" discipline of this document itself honest by describing an ADDITIVE contract, not an edit — though implementing it later will, unavoidably, require adding at minimum a way for `CollectionVaultLP` to move reserves atomically with the vault's own accounting (see NOT YET DECIDED, immediately below) since `paymentReserve`/`shareReserve` are today only mutable from WITHIN `CollectionVault.sol`'s own functions.

**NOT YET DECIDED:**
- Whether `CollectionVaultLP` becomes its own periphery contract that WRAPS the vault's reserves (requiring new vault-side functions to let an authorized LP contract move `paymentReserve`/`shareReserve` directly — a real `.sol` change to `CollectionVault.sol` when this is eventually implemented) versus a fully separate SECOND pool that simply happens to trade the same vToken (avoiding any `CollectionVault.sol` change, at the cost of fragmenting liquidity into two pools per collection, unlike anything currently in this repo). This is a real architectural fork this document does not resolve.
- Exact floor size (percentage of genesis seed vs. a fixed absolute amount).
- Whether floor-seeding happens automatically at `openPool` (protocol-enforced) or is a separate, later, treasury-optional step (opt-in, matching this repo's existing pattern of `setInventoryStake`/`setWeightModule` being separate, set-once, treasury-gated steps rather than bundled into `openPool` — Part 1 §2 `CollectionVault.sol:427-443`).
- Whether `CollectionVaultLP`'s own swap fee (if it becomes a genuinely separate pool) should route through the SAME `SWAP_SINK_SPLIT_BPS`/mandatory-sink discipline (Part 1 §2, `CollectionVault.sol:101-114`) — strong justified default: **yes**, reuse the identical mandatory-routing floor, since deviating would create a fee-routing bypass a creator/community could exploit by routing volume through the new LP pool instead of the vault's own AMM.
- Whether LP providers' positions should ALSO feed `WeightModule` signals (Part 1 §5) — strong justified default: **yes, additively**, a `noteDepth`/`noteVolume` call from `CollectionVaultLP` mirroring `_noteSwapSignals` (Part 1 §5, `CollectionVault.sol:348-352`), since more real trading depth is exactly the signal `WeightModule` already rewards, and excluding LP-pool volume would create a perverse incentive to avoid using the new pool.

### 3.2 Zap-mint for the index

**Problem, precisely stated from Part 1**: `mintProRata` and `mintSingleAsset` (Part 1 §3) both require the caller to already hold basket-native assets before minting. No path exists from "I have one arbitrary token (e.g. plain WETH, or any single already-listed constituent) and want exact IDX out" without the caller manually acquiring every constituent themselves first.

**Proposed shape — `IndexZapFacet` (working name, NOT YET DECIDED) as an ADDITIVE facet, following this repo's own existing facet-isolation discipline (Part 1 §3's `IndexCoreFacet` "smallest facet with real authority" pattern, `contracts/diamond/facets/IndexCoreFacet.sol:12-47`):**

1. `zapMint(inputToken, amountIn, desiredSharesOut, maxSlippageBps)`: caller deposits ONE input token (may or may not already be a listed constituent).
2. If `inputToken` is already a listed constituent, this collapses to `mintSingleAsset`'s existing logic (Part 1 §3, `IndexTradeFacet.sol:45-109`) — reuse that facet's function directly rather than re-implement it, per this repo's own "reuse, don't duplicate" doctrine already demonstrated by `IdxBurnAdapter`/`DividendAdapter` reusing `IndexBuybackFacet`/`_reconcileCore` (Part 1 §4).
3. If `inputToken` is NOT a listed constituent, the zap must route through a swap leg BEFORE minting. Per Part 2 §2's documented risk classes, this is the highest-risk new surface in this whole document, and the design intentionally borrows the LEAST novel mechanism available: route the swap leg through the SAME kind of AMM this repo already trusts for pricing — either (a) an already-listed `CollectionVault`'s own `buyShares`/`sellShares` if the desired constituent IS a vToken already backed by such a pool (Part 1 §2), or (b) `IndexCoinPool.swap` if the desired constituent is the index coin itself (Part 1 §2, `IndexCoinPool.sol:116-143`) — in neither case introducing a NEW external router/aggregator dependency, unlike Balancer/1inch-style zaps (Part 2 §2), because this repo's own existing pools are the only price-trusted venues already present in the codebase.
4. Per-leg AND whole-transaction slippage bounds, mirroring the standard defense from Part 2 §2: each swap leg gets its own `minOut`, and the FINAL `desiredSharesOut` is enforced the same way `mintSingleAsset` already enforces `minSharesOut` against the OBSERVED post-fee-and-allocation shares minted (Part 1 §3, `IndexTradeFacet.sol:82-88` — "the slippage guard is checked against what the DEPOSITOR actually receives, not the pre-allocation gross"), reusing that exact discipline verbatim rather than inventing a new one.
5. MEV/sandwich defense: reuse `_requirePoolQuiescent()` (already present and cited in Part 1 §3, `IndexTradeFacet.sol:53`) on every pool the zap leg touches — a zap that would need to trade against a pool that moved in the SAME block already fails closed, exactly like `mintSingleAsset` does today. This is a directly reusable existing guard, not a new invention, and directly answers Part 2 §2's "sandwich/MEV exposure" risk class using code this repo has already shipped and (per the task's own framing) presumably tested.
6. Price-impact-paid-twice (Part 2 §2/§3): explicitly accept this cost rather than pretend it away — a `zapMint` through a non-listed input token pays the swap leg's own AMM fee/impact (from whichever `CollectionVault`/`IndexCoinPool` it routes through, Part 1 §2's real fee constants: `swapFeeBps` up to `MAX_SWAP_FEE_BPS=100` bps, `IndexCoinPool.FEE_BPS=100`) on top of `mintSingleAsset`'s own existing imbalance fee (Part 1 §3, `IndexTradeFacet.sol:67-68`). Document this plainly to the caller (front-end estimate, not a contract obligation) rather than attempt to net it out — matching this repo's demonstrated preference (Part 1 §3's `mintSingleAsset` docstring) for pricing conservatively at real cost rather than subsidizing convenience.

**NOT YET DECIDED:**
- Whether `zapMint` should be restricted at genesis to ONLY input tokens that are themselves already vTokens of admitted `CollectionVault`s (i.e., "zap FROM one collection's vToken INTO the index, auto-acquiring the rest") versus accepting arbitrary ERC20 input requiring a full N-hop route — the latter reintroduces exactly the aggregator-router dependency (1inch/Paraswap-style, Part 2 §2) this repo has never used anywhere in the code read in Part 1, and would be a genuinely new trust surface (an external router contract) this document does not recommend defaulting to without a separate, dedicated security review.
- Whether the swap leg(s) should be capped by the SAME `MAX_IMPACT_BPS = 300` (3%) constant `InventoryBuyAdapter` already enforces (Part 1 §4, `InventoryBuyAdapter.sol:108`) — strong justified default: **yes**, reuse the identical 3% ceiling verbatim, matching this repo's own repeatedly-demonstrated "reuse the already-vetted ceiling" pattern (Part 1 §2's `CollectionVault.sol:127-130` doing the same for `CEIL_SINK_SPLIT_BPS`).
- Whether a failed/reverted zap should partially refund (return the un-routed input) or revert-all-or-nothing — strong justified default: **revert-all-or-nothing** for the initial version, since this repo's `mintProRata`/`mintSingleAsset` (Part 1 §3) are both already all-or-nothing, and a partial-fill zap is a materially more complex state machine that Part 1 found no precedent for anywhere in this codebase.

### 3.3 Explicit non-goals of this document

This design does not build, and does not claim to have found already built: PLANK burn/LP adapters (Pipes P/R), a deployed PLANK ERC20, a live-deployed `EnergyBus` instance, or a resolution of the vToken/xToken-vs-single-share-atom discrepancy between `docs/ONESHOT-OPUS-AXIOM-1-BULLISH-DELIVERY.md` and the actual code (all per Part 1). Those remain exactly as characterized in Part 1 — genuinely absent or genuinely unresolved, not addressed by this document.
